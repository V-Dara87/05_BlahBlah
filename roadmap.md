# blah-blah — Feature Roadmap & Flaws
 
Core goal: unify Remotion-style code-driven motion with normal editor operations (timeline placement, GUI editing), Unity-style component model. Four pillars: ECS, Timeline, Inspector, support for all web tech.
 
**Scope note (added):** not trying to be a general-purpose editor / DaVinci Resolve competitor. The actual target use case: dropping simple annotated shapes (circles, boxes, arrows) with cool web-tech-driven motion onto tutorial-style footage, easier than Resolve/Fusion, with the option to let AI author the motion logic and (later) drive it straight from narration text. Scope everything below against that, not against "as good as Resolve."
 
## P0 — Required to call the architecture "done"
 
1. **Renderer unification** — merge `SceneViewport.jsx` / `PreviewWindow.jsx` into a single `EntityRenderer.jsx`, driven by a `createRendererComponent()` factory in `ecs.js`.

2. **`CanvasRenderer`** — new component type for arbitrary web tech (Three.js, raw Canvas/WebGL, etc.), separate from `ReactRenderer`. Contract:
   ```js
   export default class MyThing {
     static props = { speed: { type: 'number', default: 1, min: 0, max: 10 } };
     onMount({ container, props, libs }) {}   // container: plain <div>, libs: injected globals (libs.THREE, libs.gsap...)
     onUpdate({ container, time, frame, props }) {}  // driven by absolute timeline time, NOT wall clock/rAF accumulation
     onUnmount() {}
   }
   ```
   - ✅ **Done.** Contract implemented in `engine/canvasRunner.js` (new file): mount/update/unmount lifecycle against a plain `<div>`, driven by absolute timeline time. Lazy CDN-global lib loading (`libs.THREE`, `libs.gsap`, plus explicit `libs.load(name)` for scripts that need to `await` a lib in `onMount`). Registered in `ecs.js` as `RENDERER_REGISTRY.CanvasRenderer`. Sample script (`CanvasOrbit.js`) + sample prefab added so it's testable today. Live in the running app since #1's wiring, and now has a real Inspector card (see #3) instead of being settable only via a prefab's default `props` object.
   - Reuses `extractScriptProps` and the Inspector's schema-driven field rendering unchanged. — *`extractScriptProps`/`compileScriptModule` reuse: done, in `canvasRunner.js`. Inspector field reuse: done — see #3, CanvasRenderer now has an "Add Component" entry and a props card driven by the same `InspectorFieldList` as ReactRenderer/ScriptComponent.*
   - `libs` injection is the pragmatic first step for "support all web tech" (CDN globals); swap for esbuild-wasm + ESM later if literal `import` syntax is wanted. The component contract doesn't change either way.
   - Watch out: libraries with their own internal clock (GSAP, some Three.js patterns) don't all support "seek to time X" cleanly — confirm each library adapter can jump to an arbitrary time before assuming scrubbing will look correct. — *Still unverified; only the no-dependency raw-Canvas2D sample script has been exercised so far. Worth doing now that CanvasRenderer props are editable end-to-end (mount → update → Inspector tweak → re-render).*
   - `ReactRenderer` stays separate for now (decided) — don't force it into this contract. Merging it later is a valid P2 cleanup (Remotion itself doesn't use separate roots — it keeps one big React tree and passes the current time/frame down), but not required for core.
3. **Unified Inspector field rendering** — one schema-driven render function used by Transform, ReactRenderer, ScriptComponent, and the new CanvasRenderer, instead of hand-written UI per component type in `UnityInspector.jsx`. Do this before/alongside #2, so CanvasRenderer doesn't add yet another hand-written Inspector block.
   - ✅ **Done.** New `components/inspector/InspectorField.jsx`: a single `InspectorField` component dispatching on `field.type` (`number`/`color`/`boolean`/`select`/`textarea`/string-fallback), plus an `InspectorFieldList` helper that renders a full schema as `.inspector-row`s with the standard "no exposed props" hint. Field shape matches `extractScriptProps`'s output exactly (`{ name, type, defaultVal, label, min, max, step, options }`), so ReactRenderer, ScriptComponent, and CanvasRenderer all now render through the same list component instead of three copies of the same switch statement (there were two before; CanvasRenderer would have made three). Transform gets a static field schema (`TRANSFORM_FIELD_GROUPS`, same shape) so its Position/Rotation/Scale/Opacity rows go through `InspectorFieldList` too, replacing the hand-written `DragNumber` calls. `UnityInspector.jsx` gained a CanvasRenderer card (icon, script-error badge, Edit JS button, remove button, props list) and an "Add Component → Canvas Components" popover section — CanvasRenderer props are now actually editable from the UI for the first time. `TextRenderer` and `ShapeRenderer` are left with their existing bespoke bodies on purpose: their fields (shape-type select, paired W/H drag-numbers) don't map cleanly onto one-field-per-row and folding them in wasn't needed to unblock CanvasRenderer. 4. **Undo/Redo** — state in `App.jsx` is a flat set of `useState` (`entities`, `tracks`, `scripts`, `prefabs`), which makes a simple snapshot-stack undo system straightforward to add. High priority: without it, testing new features (esp. #2) is riskier than it needs to be.
   - ✅ **Done.** New `hooks/useUndoableState.js`: a generic `{ past, present, future }` snapshot-stack hook. `App.jsx` now holds `entities`/`tracks`/`scripts`/`prefabs` together as one combined history value (single Ctrl+Z reverts the last logical edit across all four at once, matching how the rest of the editor treats them as one project state) instead of four independent `useState`s. `mediaAssets`, `projectName`, and selection stay outside the undo scope on purpose — asset imports and selection are housekeeping, not content edits. `setEntities`/`setTracks`/`setScripts`/`setPrefabs` wrapper functions preserve the old call signature (value or updater fn) everywhere they're already called, plus a new optional second `{ coalesce: true }` arg. `handleUpdateEntity` and `handleUpdateTrack` pass `coalesce: true` since they fire continuously during a clip drag or an Inspector number-field scrub — those merge into one undo step per gesture (400ms window) instead of one per intermediate value; every other mutation (add/delete/split clip, script/prefab edits) stays one full step per action, uncoalesced. `handleLoadDemoScene`, `handleProjectCreated`, and `handleOpenProjectFolder` call the hook's `reset()` instead of the normal setters — swapping to a different project starts a fresh (empty) undo history rather than stacking on top of, or being undoable back into, whatever was open before. `handleApplyProjectJson` (the Project Code / paste-JSON modal) now applies its `entities`/`tracks`/`scripts`/`prefabs` changes as a single combined history entry, so one Ctrl+Z reverts the whole paste. Wired to `Ctrl+Z` (undo) and `Ctrl+Shift+Z` / `Ctrl+Y` (redo) in the existing global keydown handler — placed after the `INPUT`/`TEXTAREA`/`SELECT` guard so native text-field undo still wins while typing. Added Undo/Redo buttons (`Undo2`/`Redo2` icons, disabled when the respective stack is empty) to `UnityHeader`'s quick-tools toolbar, next to Split/Delete.

Also unverified: history behavior across the hot-reload script poller (`checkScriptsForChanges`) — an external VS Code script edit calls `setScripts` like any other change and will currently push its own undo step; whether that's desirable (probably yes, keeps things reversible) or should be exempted like the reset-triggering project loads is worth a decision once it's actually exercised.

Auto-resets when the underlying script changes (`resetKey` prop), so fixing a script in `ScriptEditorModal` recovers the clip without a full reload. Live in the running app as of #1's wiring.

## P1 — Needed to call it a usable editor
 
6. **GUI keyframing** — set keyframes on Inspector fields without writing a script. This is what gives the "normal editing operations" side of the core pitch actual substance. Now that #3 gives every keyframeable field a uniform schema shape (`{ name, type, min, max, step, ... }`), this is more tractable than before — a keyframe track UI can target "a field on this schema" generically instead of per-component-type.
7. **Keyframe ⇄ script conversion** — "bake" GUI keyframes into a script, and/or bake a script's computed motion into keyframes. This is the most direct expression of the app's actual differentiator; worth prioritizing once #6 exists.
8. **Timeline snapping + multi-select** — `snappingEnabled` already exists in `App.jsx`; verify it actually works end-to-end, and add multi-clip selection/drag.
9. **Audio waveform display** — needed for any real audio timing work.
10. **Project file schema versioning** — stamp saved projects with a version and add a migration step on load. Important *now* specifically because the Renderer redesign (#1-2) will change what a saved project looks like — without this, test projects saved this week won't open next month.
11. **Resume export/render pipeline** — currently postponed on purpose until Renderer design settles; move to P1 once #1-3 land. #1, #2, and #3 have all landed now — this can move to P1. When it's picked back up, it should render off deterministic `time`/`frame` values (same principle as #2's `onUpdate`), not wall-clock playback — this is exactly the technique Remotion uses (render is a pure function of frame number, no real time elapses between frames).
 
## P1.5 — AI-assisted editing features (new, from planning discussion)
 
Not part of the core architecture pillars, but directly serve the "tutorial video annotation" use case. Each is a separate module layered on top of P0's ECS/CanvasRenderer foundation, not a P0 blocker — sequence after P0 is stable.
 
22. **Auto cut (silence removal)** — detect near-silent regions in a clip's audio track by volume/amplitude analysis (no speech-to-text needed for this part) and propose/apply cut markers on the timeline. Simplest of the three to build; pure signal analysis, no external API dependency.
23. **Speech-to-text transcription** — feed a clip's audio to an ASR API (e.g. ElevenLabs Scribe — reported ~3.1% WER on Khmer per FLEURS benchmark, meaningfully better than relying on a general OCR/segmentation pipeline for Khmer specifically, since Khmer script has no inter-word spacing and needs dedicated segmentation that off-the-shelf regex/program logic won't handle well). Output: timestamped transcript attached to the clip.
24. **Repeated-take detection** — once a transcript exists (#23), send it to an LLM (e.g. Gemini) and ask it to find repeated/re-recorded lines rather than building a bespoke text-similarity/dedup algorithm — LLM handles the language understanding (including Khmer word/meaning detection) that a hand-rolled program would struggle with. Surface suggested duplicate ranges for the user to review before cutting (do not auto-cut silently).
25. **Text → animation authoring** — given narration text (from #23) or a plain-language description, have an LLM generate a CanvasRenderer script (or GUI keyframe set, once #6/#7 exist) matching the P0 #2 contract. This is the heaviest of the four — depends on P0 #2 (contract must be stable) and P0 #5 (a bad LLM-generated script must not crash the editor, which is exactly what the error boundary is for). Treat LLM output as untrusted input requiring the same script-error handling as hand-written scripts.

## Flaws found in current code (not yet on the list above)
 
- **`transpileJsxToJs` in `scriptRunner.js`** is a hand-rolled regex-based JSX transpiler (iterative regex passes for nested tags, manual brace-counting for expressions). It works for the current sample scripts but is fragile — deeply nested or unusual JSX patterns can silently mis-transpile rather than error clearly. Worth budgeting time to either harden it or accept its limits explicitly (document what JSX patterns are NOT supported) before users write ambitious scripts against it.
- **`extractScriptProps`'s regex** (`(?:static\s+props|\bprops)\s*=\s*(\{[\s\S]*?\n\s*\};?)`) is non-greedy and looks for the first `\n  };`-shaped close. A `props` object containing a nested multi-line object as a default value could get truncated early. Low risk today (all current scripts are simple), worth a test case once CanvasRenderer scripts get more complex — and now more scripts are reachable via the Inspector's "Canvas Components" list (#3), so this is worth doing sooner.
- **No schema version on saved projects** (see P1 #10) — flagged separately because it's a correctness/data-loss risk, not just a missing feature.
